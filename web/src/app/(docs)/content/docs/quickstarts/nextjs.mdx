## Set up Kizlo in a new project

Starting fresh? Scaffold a Next.js app with Kizlo already wired:

```package-install
npx kizlo@latest create nextjs my-app
```

It scaffolds a fully wired project and walks you through your WordPress credentials. When it
finishes, `cd my-app`.

## Set up Kizlo in an existing project

Add Kizlo to an app you already have. Use the CLI (recommended) or wire the files by hand. Both
produce the same result.

### CLI setup (recommended)

Run the initializer in your project root:

```package-install
npx kizlo@latest init
```

It detects your framework, `src` dir (if present), package manager, import alias, etc. and scaffolds:

<Files>
  <Folder name="src" defaultOpen>
    <Folder name="app" defaultOpen>
      <Folder name="api" defaultOpen>
        <Folder name="kizlo" defaultOpen>
          <Folder name="[[...rest]]" defaultOpen>
            <File name="route.ts" />
          </Folder>
        </Folder>
      </Folder>
    </Folder>
    <Folder name="lib" defaultOpen>
      <Folder name="kizlo" defaultOpen>
        <Folder name="server" defaultOpen>
          <File name="index.ts" />
            <Folder name="generated">
              <File name="contract.json" />
              <File name="index.ts" />
            </Folder>
        </Folder>
        <File name="client.ts" />
      </Folder>
    </Folder>
  </Folder>
  <File name="kizlo.config.ts" />
  <File name=".env" />
</Files>

Along the way it asks whether to run WordPress locally in Docker or connect your own, writes
the matching credentials to `.env`, and generates the contract. When `init` finishes, you're
ready to make your first call.

<Callout>
  Feel free to customize this folder structure however you like. Point the `dir` option in
  `kizlo.config.ts` at it, so kizlo knows where your server files and kizlo instance live and can
  generate the server contract.
</Callout>

### Manual setup

Prefer to wire it yourself? Create the same files the CLI would.

<Steps>

<Step>

#### Install the package

```package-install
npm install kizlo@latest
```

</Step>

<Step>

#### Add `kizlo.config.ts`

Add this at your project root. It tells the CLI where Kizlo lives and which import alias to use:

```ts title="kizlo.config.ts"
import { defineConfig } from "kizlo"

export default defineConfig({
  dir: "src/lib/kizlo",
  alias: "@",
})
```

</Step>

<Step>

#### Create the server

At `src/lib/kizlo/server/index.ts`. `nextjs()` reads the framework environment and maps its Kizlo values:

```ts title="src/lib/kizlo/server/index.ts"
import { createKizlo } from "kizlo"
import { nextjs } from "kizlo/nextjs/server"

export const { procedures, client, context, handler } = createKizlo({
  integrations: [nextjs()],
})
```

</Step>

<Step>

#### Mount the route handler

At `src/app/api/kizlo/[[...rest]]/route.ts`, re-export the server's `handler` for every method:

```ts title="src/app/api/kizlo/[[...rest]]/route.ts"
import { handler } from "@/lib/kizlo/server"

export { handler as GET, handler as POST, handler as PUT, handler as PATCH, handler as DELETE, handler as OPTIONS }
```

</Step>

<Step>

#### Generate the contract

So `server/generated/` exists before the client imports it:

```package-install
npx kizlo generate
```

</Step>

<Step>

#### Create the client

Create `src/lib/kizlo/client.ts` from the generated contract. It is typed automatically:

```ts title="src/lib/kizlo/client.ts"
import { createKizloClient } from "kizlo/nextjs"
import { contract } from "./server/generated"

export const client = createKizloClient(contract)
```

</Step>

<Step>

#### Environment

Finally, connect WordPress. Use a local stack while you build and your hosted WordPress in production.

#### Local

Let Kizlo run WordPress for you. There is nothing to fill in:

```package-install
npx kizlo dev
```

It starts WordPress in Docker, writes its dev credentials to `.env` for you, and watches your server files
to keep the contract in sync. This gives you one command for the whole local loop.

#### Remote

For your hosted WordPress, add its credentials to `.env`:

```bash title=".env"
KIZLO_WP_URL=https://your-site.com
KIZLO_WP_USERNAME=admin
KIZLO_WP_APP_PASSWORD=xxxx xxxx xxxx xxxx xxxx xxxx
KIZLO_WP_SECRET=                   # a long random string
NEXT_PUBLIC_KIZLO_BASE_URL=http://localhost:3000/api/kizlo
```

Generate `KIZLO_WP_SECRET` with `openssl rand -hex 32`. While developing, run `npx kizlo dev` to keep
the generated contract in sync as you edit your server files.

</Step>

</Steps>

## Forward trusted visitor IPs on Cloudflare

For Next.js or vinext behind Cloudflare, register its geo adapter through your platform integration:

```ts title="src/lib/kizlo/server/index.ts"
import { createIntegration, createKizlo, geoCloudflareNext } from "kizlo"
import { nextjs } from "kizlo/nextjs/server"
import { introspection } from "./generated"

const cloudflare = createIntegration({
  id: "cloudflare",
  adapters: { geo: geoCloudflareNext() },
})

export const { client, handler } = createKizlo({
  integrations: [nextjs(), cloudflare],
  introspection,
})
```

Kizlo forwards the configured geo adapter's valid `ip` to WordPress as `x-real-ip`, including for
WooCommerce calls. `geoCloudflareNext()` reads `CF-Connecting-IP` from HTTP requests or lazy,
request-local `next/headers` for direct server calls. Missing request context and invalid IPv4/IPv6
values produce no visitor header. Without a geo adapter, forwarding stays off; existing geo
configurations now forward their valid IP.

### Trust your ingress

<Callout type="warn">
  Register this adapter only when your ingress guarantees that Cloudflare supplies `CF-Connecting-IP` and
  callers cannot bypass it or forge that header. Kizlo validates the address format, not the sender.
  It never falls back to incoming `x-real-ip` or `x-forwarded-for`.
</Callout>

Your storefront Worker and Cloudflare-proxied WordPress hostname must be in the **same Cloudflare
zone**. Cross-zone Worker subrequests replace the visitor address with Cloudflare's shared Worker IP;
forwarding alone cannot override that behavior. See [Cloudflare's subrequest rules](https://developers.cloudflare.com/fundamentals/reference/http-headers/#cf-connecting-ip-in-worker-subrequests).
Use the final WordPress URL: requests carrying a visitor IP reject redirects to avoid leaking it to
another destination. Private cart, checkout, and session responses must remain uncached. A geo adapter
that reads request headers can make an SSR route dynamic; avoid visitor-specific lookups for shared static data.

### Use another platform

Your framework or platform integration should supply `adapters.geo`. On Vercel, use `geoVercelNext()`;
for other providers, implement the [geo adapter contract](/docs/reference/functions/create-geo-adapter).
No separate client-IP option is needed. Return `ip: null` when the address is unknown; use
`geoMock({ ip: null })` in tests that should not forward a simulated visitor.

Register a platform integration after the framework integration to override its geo adapter. Forwarding
is limited to the configured WordPress origin; browser cookies and unrelated incoming headers are never
copied. Unexpected adapter errors produce the usual WordPress transport error, and timeouts and aborts
cover the lookup too.

### Replace an existing workaround

Keep an existing fetch wrapper until a released Kizlo version includes geo-based forwarding. When migrating,
remove the wrapper and its fetch-patch initialization together, then verify visitor IPs at WordPress
for homepage SSR and browser API calls, repeat homepage/filter checks, and check guest carts and
signed-out checkout protection before removing the working deployment mitigation.

## Render a post

Here is a complete dynamic blog post route. A single Server Component fetches
the post by slug and, alongside the markup, wires up everything a real post page needs:

- **`generateMetadata`**: title, description, canonical, Open Graph, and Twitter tags. Kizlo's
  `createPageMetadata` maps the post's SEO straight into Next.js `Metadata`, so you don't hand-write tags.
- **JSON-LD**: the post already carries `schema.org` structured data at `post.seo.schema`; render it
  with `<SeoSchema />` for rich results.

Each route renders on demand for its slug, so there's no build-time list step.

```tsx title="src/app/blog/[slug]/page.tsx"
import { createPageMetadata, SeoSchema } from "kizlo/nextjs/server"
import { notFound } from "next/navigation"
import { client } from "@/lib/kizlo/server"

type Props = { params: Promise<{ slug: string }> }

// SEO tags (title, canonical, Open Graph, Twitter) from the post's SEO head.
export async function generateMetadata({ params }: Props) {
  const { slug } = await params
  const { data: post } = await client.posts.get({ params: { identifier: slug } })
  if (!post?.seo) return {}
  return createPageMetadata(post.seo.head)
}

export default async function PostPage({ params }: Props) {
  const { slug } = await params
  const { data: post, error } = await client.posts.get({ params: { identifier: slug } })

  if (error) notFound()

  return (
    <article>
      {/* JSON-LD structured data for rich results. */}
      <SeoSchema schema={post.seo?.schema} />
      <h1>{post.title}</h1>
      <div dangerouslySetInnerHTML={{ __html: post.content ?? "" }} />
    </article>
  )
}
```
