title: createEventHandler
description: Handle a WordPress webhook event inside an integration.
---

Import `createEventHandler` from `kizlo/server` and pass the result in `createWebhookHandler({ secret, events })`. All matching handlers are awaited. Optional failures are logged; required failures reject acknowledgement for retry.

## Parameters

It takes two forms:

```ts
createEventHandler(handler)         // receive every built-in event
createEventHandler(events, handler) // declare custom events, then receive only those
```

### `events`

Optional. An array declaring the custom event types this handler accepts and a schema for each one's `data`. Omit
it to receive every built-in WordPress event instead. Each entry:

  path="../packages/kizlo/src/webhook/index.ts"

  type={`AnyEvents[number]`}
/>

### `handler`

`(event, context) => void | Promise<void>`. Runs for each matching event. It receives:

- **`event`**: the `{ type, data }` payload, or `null` when the request carries no recognized event. With
  `events` declared, `event` is narrowed to your union, so switching on `event.type` types `event.data`. Without
  it, `event` is the built-in event shape.
- **`context`**: `WebhookContext`, containing `request`, response `headers`, and an error logger.

## Returns

An `EventHandler`. List it in `createWebhookHandler`'s `events` array.

## Examples

Handle built-in events by switching on `event.type`. Each case narrows `event.data`:

```ts title="src/lib/kizlo/server/cache/index.ts"
import { createEventHandler } from "kizlo/server"

export const onContentChange = createEventHandler(async (event, context) => {
  if (!event) return

  switch (event.type) {
    case "post.updated": // event.data → { post_id, post_type }
      await revalidatePath(`/posts/${event.data.post_id}`)
      break
    case "term.deleted": // event.data → { term_id, taxonomy, post_types, count }
      context.logger.error("term removed", { id: event.data.term_id })
      break
  }
})
```

Handle a custom event by declaring its type and `data` schema first, so the handler is typed to that union.
Your WordPress plugin emits it with [`kizlo_emit_event`](/docs/php/functions/emit-event):

```ts
import { createEventHandler } from "kizlo/server"
import { z } from "zod"

export const onReview = createEventHandler(
  [{ types: ["review.created"], data: z.object({ review_id: z.number(), rating: z.number() }) }],
  async (event, context) => {
    if (event?.type !== "review.created") return
    context.logger.error("new review", { rating: event.data.rating }) // data is typed
  },
)
```

## Require success before acknowledging

Set `failureMode: "retry"` on an `EventHandler`; the default is `"log"`:

```ts
const requiredHandler = {
  ...createEventHandler(async (event, context) => {
    if (!event) return
    await updateSearchIndex(event)
  }),
  failureMode: "retry" as const,
}
```

Every matching handler finishes even when another fails. A required failure returns 503, or 429 with
`Retry-After` when rate limiting is identified; detailed errors stay in server logs. For retry-mode handlers
with explicit schemas, the type matches first and that schema validates before permissive built-in schemas.
Malformed matched data returns 422 rather than a successful no-op. Default handlers retain legacy validation.

The [optional Cloudflare revalidator](/docs/quickstarts/cloudflare#revalidate-on-wordpress-changes) opts into
this mode. A retried request can rerun successful handlers too. Make side effects idempotent and use the
logical ID from `context.request?.headers.get("webhook-id")` when needed. See
[delivery and recovery](/docs/php/functions/emit-event#delivery-and-recovery) for sender guarantees.
